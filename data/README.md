# Data sources

Everything here is small, reproducible and committed deliberately. Nothing in
this repo contains real personal, proprietary or confidential data.

Regenerate the whole directory with:

```bash
python scripts/gen_vendor_master.py
```

---

## 1. `sample/vendor_master.json` — internal vendor master

| | |
|---|---|
| Origin | **Synthetic.** Generated by `scripts/gen_vendor_master.py`, seeded with `SEED = 42` |
| Records | 200 vendors |
| Licence | Ours; no restrictions |
| Represents | The internal procurement system an organisation actually runs on — the data Zetaris exists to serve |

This stands in for an ERP vendor extract. It is synthetic on purpose: a real
vendor master is confidential, and the hackathon guidance is explicit about
avoiding private or real personal data.

### Planted cases — the point of the file

The mess is deliberate. Each case exercises a specific agent behaviour, and a
run that gets all seven right is the demo.

| Vendor | Case | Correct outcome |
|---|---|---|
| `V0001` Zarechny Trading Ltd | Alias/transliteration differs from the list spelling | **BLOCK** — alias hit |
| `V0002` Harbourgate Components GmbH | Clean itself; ultimate parent is listed. Bank country also disagrees with registered country | **BLOCK** via the control chain (Day 4) |
| `V0003` Zarechnyy Logistics Pte Ltd | Near-miss: similar name, different jurisdiction | **CLEAR** — must not be blocked |
| `V0004` Global Trading Ltd | Generic name, no tax ID | **ESCALATE** — unresolvable |
| `V0005` International Services LLC | Generic name, no tax ID | **ESCALATE** — unresolvable |
| `V0006` / `V0007` Copperline Industries | Same real entity, two IDs, two spellings, one missing tax ID | Deduplicate |

Plus, across the filler rows:

- **Suffix variation** — `Ltd` / `Limited` / `LLC` / `L.L.C.` / `GmbH` / `B.V.` / `Pte Ltd` / `Inc` / `S.A.`
- **~17% missing `tax_id`** — this is what makes the data-quality branch real rather than theatrical. The agent reads the null rate at runtime and raises its evidence bar because of it.

`_planted_cases` in the JSON maps each vendor ID to why it exists. It is
metadata for reviewers, not an input to the agents — nothing in `clearline/`
reads it, so the system cannot cheat by looking up the answers.

## 3. Planned for Day 2

| Source | Access | Notes |
|---|---|---|
| **GLEIF LEI** <https://api.gleif.org/api/v1> | Open, no key | `/lei-records/{lei}/direct-parent`, `/ultimate-parent`, `/direct-children` — the control chain. Rate-limited, so cache aggressively |
| **SEC EDGAR** <https://data.sec.gov> | Open | **403s without a descriptive `User-Agent`** — set it in the REST table's `HEADER()` block |

### An accuracy limit worth stating plainly

GLEIF reports **control and accounting-consolidation relationships, not
ownership percentages**. Clearline therefore never asserts a percentage.
OFAC's 50% rule needs ownership data these sources do not provide, so any
indirect finding is surfaced as a control relationship and flagged for human
confirmation.

## Shape

Each file is a JSON **object** with its records under one key (`vendors`,
`entities`), not a bare array. That is the shape Zetaris's REST tables handle:
an object at the root, arrays flattened with `LATERAL VIEW explode()`. See
`sql/02_rest_tables.sql`.

## How Zetaris reaches these files

It cannot read your host filesystem. `scripts/sidecar.sh` serves this directory
from a container on the Zetaris Docker network, so the files are reachable at
`http://clearline-data/<file>` from inside the platform. No S3 account, no edits
to the Zetaris bundle.
